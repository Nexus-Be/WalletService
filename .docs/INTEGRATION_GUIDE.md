# Wallet Service Integration Guide

This guide is for the frontend, API gateway, payment providers, and services that
call or exchange events with Wallet.Api. It documents the current implementation,
not an aspirational contract. The protobuf schema is
`Wallet.Api/Contracts/shop.proto`; REST routes and behavior are implemented in
`Wallet.Api/Services/WalletHttpEndpoints.cs`.

## At a glance

- The service exposes wallet REST endpoints under `/api/v1/wallets`, plus the
  legacy `WalletApi` gRPC service.
- The API does not authenticate bearer tokens itself. The gateway must
  authenticate the caller and supply trusted `x-user-id` and `x-user-role`
  headers on protected requests.
- Wallets are provisioned in VND by default, and VNPay top-ups are VND-only.
  Top-ups are completed only after a valid IPN; initiating a payment does not
  credit the balance.
- Checkout debits and refunds are event-driven. Withdrawal requests reserve
  funds until an administrator approves or rejects them.
- Do not treat a browser return/redirect or a payment-initiation response as
  proof of payment. Use the resulting service state or the documented events.

## Authentication and gateway responsibilities

For protected REST requests, Wallet.Api reads:

| Header | Required value |
|---|---|
| `x-user-id` | Authenticated user's non-empty UUID |
| `x-user-role` | One or more verified roles, comma-separated or repeated; comparisons are case-insensitive |
| `x-client-ip` | Original client IP for top-up initiation; if omitted, the API uses the connection IP |

The gRPC service reads the same values from gRPC metadata. It falls back to the
gRPC peer address for `x-client-ip` if that metadata is absent.

The gateway must remove or overwrite identity and role headers supplied by the
browser or another untrusted caller. Never expose a route that lets a client
choose its own `x-user-id` or `x-user-role`. The service trusts these headers;
they are not a substitute for gateway authentication.

Roles enforced by the current endpoints:

| Operation | Accepted role |
|---|---|
| Read own wallet or transactions | `BUYER`, `SELLER`, `ADMIN` |
| Initiate VNPay top-up or direct payment | `BUYER`, `SELLER` |
| Request a withdrawal | `SELLER` |
| Approve/reject a withdrawal | `ADMIN`, `SUPPORT_STAFF` |
| Adjust a wallet balance | `ADMIN` |

REST read endpoints always use the authenticated user; they do not accept a
target user ID. The gRPC `GetWallet` and `ListTransactions` allow `ADMIN` to
select a target through the request's `user_id`. For non-admin gRPC callers,
the request `user_id` is ignored in favor of the authenticated identity.

## REST API

All paths below are relative to the Wallet.Api host. JSON uses camel-case
property names. Unless noted otherwise, successful responses use this envelope:

```json
{
  "success": true,
  "statusCode": 200,
  "message": null,
  "data": {},
  "traceId": "00-...",
  "timestamp": "2026-10-27T00:00:00+00:00"
}
```

The `timestamp` is generated by the API in UTC. The actual HTTP status is also
returned as `statusCode`. VNPay IPN is the exception: it returns the provider
response directly as `{ "RspCode": "...", "Message": "..." }`.

### Read wallet

`GET /api/v1/wallets/me`

Roles: `BUYER`, `SELLER`, `ADMIN`. The response `data` contains:

```json
{
  "walletId": "wallet-uuid",
  "userId": "user-uuid",
  "balance": 500000.00,
  "lockedBalance": 0.00,
  "availableBalance": 500000.00,
  "currency": "Vnd",
  "status": "ACTIVE",
  "updatedAt": "2026-10-27T00:00:00+00:00"
}
```

`availableBalance` is `balance - lockedBalance`. A non-active wallet returns
`403 WALLET_LOCKED`. The currency string is currently produced from the
`CurrencyCode` enum (`Vnd`). The ordinary gRPC wallet/transaction mappings use
the same spelling; top-up responses and payment flows use `VND`. Clients should
compare currency values case-insensitively.

### List transactions

`GET /api/v1/wallets/transactions?page=1&limit=20&type=DEPOSIT&fromDate=...&toDate=...`

Roles: `BUYER`, `SELLER`, `ADMIN`. The authenticated caller's transactions are
returned; this route has no user-ID override. `page` defaults to 1 and `limit`
defaults to 20; `limit` must be between 1 and 100. `fromDate` and `toDate` are
inclusive ISO-8601 date/time filters and `fromDate` must not be later than
`toDate`.

Supported `type` filters are `ALL`, `DEPOSIT`, `WITHDRAWAL`, `PAYMENT`,
`REFUND`, or a `WalletTransactionType` enum name. The API sorts newest first.
The response `data` is:

```json
{
  "items": [
    {
      "id": "transaction-uuid",
      "type": "DEPOSIT",
      "amount": 100000.00,
      "balanceAfter": 600000.00,
      "status": "Success",
      "note": "",
      "createdAt": "2026-10-27T00:00:00+00:00"
    }
  ],
  "pagination": {
    "pageIndex": 1,
    "pageSize": 20,
    "totalCount": 1,
    "totalPages": 1,
    "hasPreviousPage": false,
    "hasNextPage": false
  }
}
```

REST transaction amounts are signed for display: debits (payments,
withdrawals, transfer-out, and debit adjustments) are negative; credits are
positive. The response intentionally exposes the REST transaction type
categories rather than the full ledger enum for common types:

| Ledger types | REST type |
|---|---|
| `TopupVnpay` | `DEPOSIT` |
| `WithdrawalDebit`, `WithdrawalReversal` | `WITHDRAWAL` |
| `PurchaseDebit`, `DirectGatewayPayment` | `PAYMENT` |
| `RefundCredit` | `REFUND` |
| Other types | Uppercase enum name |

The `type` filter accepts the categories above and raw enum names. `ALL` means
no type filter.

REST serializes monetary values as JSON numbers, while the gRPC contract and
events use decimal strings. Parse/format money with decimal arithmetic in
clients rather than binary floating-point arithmetic.

### Initiate a VNPay top-up

`POST /api/v1/wallets/topups/vnpay`

Roles: `BUYER`, `SELLER`. Request:

```json
{
  "amount": 100000.00,
  "bankCode": "optional-bank-code",
  "returnUrl": "https://shop.example.com/wallet/topup/return"
}
```

`amount` must be between 10,000 and 100,000,000 VND, positive, and have no more
than two decimal places. `returnUrl` must be an absolute HTTPS URL. `bankCode`
is optional. The gateway must supply a valid `x-client-ip` or preserve the
client connection IP.

Success is HTTP `201 Created`; `data` contains:

```json
{
  "topupId": "topup-uuid",
  "paymentUrl": "https://sandbox.vnpayment.vn/...",
  "txnRef": "TOPUP-...",
  "expiresIn": 900
}
```

Send the user to `paymentUrl`. The current response advertises `expiresIn` as
900 seconds; the top-up handler does not itself enforce an expiration deadline.
The top-up remains pending and the wallet balance is unchanged until a
signature-valid VNPay IPN succeeds. The request has no idempotency key; retrying
after an uncertain network failure can create another pending top-up with a
different reference.

### VNPay IPN

`POST /api/v1/wallets/vnpay/ipn`

This is the public provider callback; it does not use caller identity headers.
The handler accepts form data or a JSON object of VNPay parameters and validates
`vnp_SecureHash` using the configured hash secret before changing state. The
VNPay merchant configuration must point its server-to-server IPN callback to
this route. The `returnUrl` passed during initiation is the browser return
destination; it is not the IPN route.

Possible responses include:

| `RspCode` | Meaning |
|---|---|
| `00` | Callback accepted (successful or failed VNPay payment response processed) |
| `01` | Top-up reference not found |
| `02` | Already processed or top-up is no longer pending |
| `04` | Amount does not match the stored top-up |
| `97` | Invalid signature or malformed callback body |

The service credits the wallet only when the signature is valid, the callback
amount matches the stored amount, and VNPay's `vnp_ResponseCode` is `00`.
Clients should refresh wallet/transaction state after returning to the site;
the browser return alone does not establish settlement.

### Initiate direct-gateway payment

`POST /api/v1/wallets/checkout/direct`

Roles: `BUYER`, `SELLER`. Request:

```json
{
  "orderId": "order-uuid",
  "amount": 250000.00,
  "gateway": "example",
  "bankCode": "optional-bank-code",
  "returnUrl": "https://shop.example.com/checkout/return"
}
```

`returnUrl` must be HTTPS. `orderId` must be a non-empty UUID; `amount` must be
positive with at most two decimal places. The gateway name must have a matching
`PaymentGateways:{gateway}` configuration. The returned `paymentUrl` is signed
by Wallet.Api and `status` is `PENDING`.

Important limitation: the current implementation only initiates the external
payment and persists a pending `DirectGatewayPayment` transaction. It has no
provider callback/settlement consumer for this direct-gateway flow, so it does
not debit or credit the wallet and does not mark the transaction paid. Do not
use this route as a completed checkout signal until a settlement flow is
implemented. Repeating the same pending order/payment details reuses the
transaction; conflicting data for that order is rejected.

### Request a seller withdrawal

`POST /api/v1/wallets/withdrawals`

Role: `SELLER`. Request:

```json
{
  "amount": 50000.00,
  "bankCode": "Example Bank",
  "accountNumber": "123456789",
  "accountHolderName": "SELLER NAME"
}
```

The amount must be at least 50,000 VND and have at most two decimal places.
The endpoint currently passes `bankCode` into the application's `BankName`
field; send the bank name there. The other bank fields are required and
length-limited.

Success is HTTP `201 Created`; response `data` includes `withdrawalId`,
`amount`, `fee`, `status` (`PENDING`), and `requestedAt`. The current fee is
zero. The full requested amount is locked immediately, reducing
`availableBalance` without reducing `balance`. Approval later deducts it from
both the locked balance and wallet balance; rejection releases the lock.
There is no seller-facing withdrawal status/list route in the current API.

### Approve or reject a withdrawal

`PATCH /api/v1/admin/wallets/withdrawals/{id}`

Roles: `ADMIN`, `SUPPORT_STAFF`. Request:

```json
{
  "action": "APPROVE",
  "adminNote": null
}
```

`action` is `APPROVE` or `REJECT`, case-insensitive. `adminNote` is required
when rejecting and becomes the rejection reason. The response `data` contains
`withdrawalId`, `status`, `processedAt`, and `transactionId` (null when
rejected). Only pending withdrawals can be processed.

### Admin balance adjustment

`POST /api/v1/admin/wallets/{walletId}/adjustments`

Role: `ADMIN`. `walletId` is the wallet UUID, not the user UUID. Request:

```json
{
  "amount": 10000.00,
  "adjustmentType": "CREDIT",
  "reason": "Support case reference"
}
```

`adjustmentType` is `CREDIT` or `DEBIT`; amount must be positive with at most
two decimal places, and reason is required (maximum 500 characters). A debit
cannot exceed available balance. Success response `data` contains
`adjustmentId`, `walletId`, `amount`, `balanceAfter`, and `createdAt`.

## HTTP error handling

Errors use this shape (the `errors` property may be null):

```json
{
  "type": "https://tools.ietf.org/html/rfc9110#section-15.5.1",
  "title": "Bad request",
  "status": 400,
  "errorCode": "VAL_INVALID_INPUT",
  "detail": "One or more validation errors occurred.",
  "errors": {
    "Amount": ["..."]
  },
  "traceId": "00-...",
  "timestamp": "2026-10-27T00:00:00+00:00"
}
```

Common codes/statuses:

| HTTP | Error code | Typical cause |
|---|---|---|
| `400` | `VAL_INVALID_INPUT`, `VAL_INVALID_AMOUNT`, `MIN_WITHDRAWAL_LIMIT`, `ALREADY_PROCESSED` | Invalid request/validation or already-processed withdrawal |
| `401` | `UNAUTHORIZED` | Missing/invalid `x-user-id` |
| `403` | `FORBIDDEN`, `WALLET_LOCKED` | Role not allowed or wallet is not active |
| `404` | `WALLET_NOT_FOUND`, `WITHDRAWAL_NOT_FOUND` | Wallet or withdrawal does not exist |
| `400` | `INSUFFICIENT_BALANCE` | Not enough available balance |
| `409` | Business-rule error code | Conflict such as a duplicate key with different data |

Validation details are grouped under `errors` by property name. Preserve
`traceId` when surfacing a support issue. The API does not currently map
unexpected exceptions through the same error envelope.

## gRPC contract

The `WalletApi` service lives in `Wallet.Api/Contracts/shop.proto` under package
`shoppingcart.v1` and C# namespace `ShoppingCart.Contracts.V1`. The shared
protobuf schema is versioned; make only additive schema changes and do not
reuse field numbers.

| RPC | Behavior and integration note |
|---|---|
| `GetWallet(UserRequest)` | Returns the authenticated caller's wallet. `ADMIN` may use `user_id` to select another user. |
| `Deposit(WalletDepositRequest)` | Initiates a VNPay top-up; requires BUYER/SELLER, positive amount, VND (or empty currency), and `payment_method = VNPAY`. `user_id` is ignored in favor of caller metadata. The payment URL is in `WalletTransaction.note`; status is `PENDING`. |
| `Withdraw(WalletWithdrawRequest)` | Returns `UNIMPLEMENTED`. Use the REST withdrawal flow. |
| `Transfer(WalletTransferRequest)` | Transfers between wallets for BUYER/SELLER. The sender is always the authenticated caller; request `sender_user_id` is not used. Returns the sender's transfer-out transaction. |
| `ListTransactions(WalletTransactionsRequest)` | Returns a page for the caller; `ADMIN` may select another `user_id`. Request `page` must be positive; non-positive `page_size` defaults to 20 and maximum is 100. No date filters are available on this RPC. |

All protected RPC calls require gRPC metadata `x-user-id` and `x-user-role`.
The current gRPC code accepts `BUYER`, `SELLER`, and `ADMIN` for reads,
`BUYER`/`SELLER` for deposits and transfers. `SUPPORT_STAFF` is not accepted
by these RPCs.

Money fields in the protobuf are strings. Amount parsing uses invariant
culture; wallet and transaction amount outputs use two decimal places. Wallet
timestamps are round-trip ISO-8601 strings. The legacy `Wallet` message contains
balance, currency, status, and updated time, but no locked or available
balance; use REST `GET /api/v1/wallets/me` when those are needed. gRPC
transaction types are raw enum names (for example `TopupVnpay`), and amounts
are unsigned ledger amounts; the signed display convention described for REST
does not apply.

## Events for service integrations

Wallet.Api uses MassTransit with RabbitMQ and an EF Core transactional outbox.
Consumer endpoints are configured from consumer class names using the
kebab-case endpoint formatter. Integrating producers and consumers must use
the shared event contracts in `Wallet.Domain/Events/WalletEvents.cs`, including
the same property names and types. IDs are UUID strings; money values are
invariant-culture decimal strings; event timestamps are `DateTimeOffset`.

### Events consumed by Wallet.Api

| Contract | Required properties | Effect |
|---|---|---|
| `IUserRegisteredEvent` | `UserId` | Creates an ACTIVE VND wallet with zero balance if one does not already exist. |
| `IOrderCheckoutRequestedEvent` | `OrderId`, `UserId`, `Amount` | Debits the buyer's available wallet balance and publishes `IWalletDebitSucceededEvent` or `IWalletDebitFailedEvent`. |
| `IStockReservedEvent` | `OrderId`, `ReservationId`, `UserId`, `TotalAmount`, `Timestamp` | Legacy checkout debit path; publishes `IPaymentCompletedEvent` or `IPaymentFailedEvent`. |
| `IOrderCancelledEvent` | `OrderId`, `CancellationId`, `UserId`, `Amount`, `Reason` | Refunds a previously paid order and publishes `IWalletRefundedEvent`. |

Checkout amount strings must parse as invariant decimals. Order, user, and
cancellation IDs must be non-empty UUIDs. The debit is keyed by `OrderId`: a
matching already-successful debit does not debit twice; conflicting data for
the same order produces a failure result. The refund is keyed by
`CancellationId`, must refer to an existing successful purchase, and cannot
exceed the original paid amount after prior refunds.

### Events published by Wallet.Api

| Contract | Payload properties |
|---|---|
| `IWalletTopupInitiatedEvent` | `WalletId`, `TransactionReference`, `Amount`, `Timestamp` |
| `IWalletTopupSucceededEvent` | `WalletId`, `TransactionId`, `Amount`, `Timestamp` |
| `IWalletTopupFailedEvent` | `WalletId`, `TransactionReference`, `Reason`, `Timestamp` |
| `IWalletDebitSucceededEvent` | `OrderId`, `TransactionId`, `Amount`, `Timestamp` |
| `IWalletDebitFailedEvent` | `OrderId`, `Reason`, `Timestamp` |
| `IPaymentCompletedEvent` | `OrderId`, `TransactionId`, `Amount`, `Timestamp` |
| `IPaymentFailedEvent` | `OrderId`, `Reason`, `Timestamp` |
| `IWalletRefundedEvent` | `OrderId`, `TransactionId`, `Amount`, `Timestamp` |
| `IWithdrawalRequestedEvent` | `WithdrawalId`, `WalletId`, `Amount`, `NetAmount`, `Timestamp` |
| `IWithdrawalApprovedEvent` | `WithdrawalId`, `WalletId`, `Amount`, `NetAmount`, `ProcessedBy`, `Timestamp` |
| `IWithdrawalRejectedEvent` | `WithdrawalId`, `WalletId`, `Reason`, `ProcessedBy`, `Timestamp` |
| `IDirectPaymentInitiatedEvent` | `OrderId`, `TransactionId`, `Gateway`, `Amount`, `Timestamp` |
| `IDirectPaymentFailedEvent` | `OrderId`, `Gateway`, `Reason`, `Timestamp` |

For the newer checkout path, the order service should react to wallet-debit
success/failure contracts. The legacy stock-reserved path uses the older
payment-completed/payment-failed contracts. Do not assume both result event
families are emitted for one debit.

## Payment provider and deployment configuration

Configure these values outside source control, using secrets management in
deployed environments:

| Configuration key | Purpose |
|---|---|
| `ConnectionStrings:DefaultConnection` | PostgreSQL wallet database |
| `RabbitMq:Host`, `Port`, `User`, `Password` | RabbitMQ connection |
| `VnPay:PaymentUrl` | VNPay checkout URL |
| `VnPay:TmnCode`, `HashSecret` | VNPay merchant identity and HMAC-SHA512 signing/verification secret |
| `VnPay:ReturnUrl` | Default HTTPS browser return URL when no per-request return URL is supplied |
| `VnPay:Version` | VNPay protocol version |
| `PaymentGateways:{gateway}:PaymentUrl` | HTTPS payment URL for a direct provider |
| `PaymentGateways:{gateway}:SigningSecret` | HMAC-SHA512 secret for that direct provider |
| `Otel:Endpoint` | OpenTelemetry collector endpoint |

VNPay IPN validates the signed parameter set with fixed-time signature
comparison. Do not implement settlement from unsigned browser parameters.
Direct-gateway URLs are signed over
`orderId|amount|currency|bankCode|returnUrl`; the provider must understand the
query parameters appended by Wallet.Api and independently validate the
signature. Example placeholders in `Wallet.Api/appsettings.example.json` are
not production credentials.

The service uses PostgreSQL row locks for balance-changing operations. Confirm
that the target database has the tables/indexes required by the current EF
model and MassTransit inbox/outbox before deployment; this repository state
does not include a migration for all of the added wallet workflow schema.

## Known integration gaps and cautions

- The direct-gateway flow has no implemented settlement callback/consumer.
  Initiation is not payment completion.
- The VNPay browser return route is owned by the frontend; Wallet.Api's
  server-to-server IPN route is `/api/v1/wallets/vnpay/ipn`.
- The legacy gRPC `Withdraw` RPC is intentionally unimplemented. Use
  `POST /api/v1/wallets/withdrawals` and the admin PATCH route.
- The withdrawal request field is named `bankCode` in HTTP JSON but is stored
  as the bank name. The current withdrawal fee is zero.
- Top-up and withdrawal request bodies do not accept idempotency keys. Avoid
  blind retries after timeouts; refresh wallet/transaction state before
  submitting again.
- REST wallet responses include locked and available balances; the legacy
  protobuf wallet response does not.
- Wallet provisioning, checkout debit, and refunds are event-driven. A frontend
  cannot directly create a wallet or invoke those flows through a REST route.
- The REST withdrawal API currently has no endpoint for listing or retrieving
  withdrawal requests.
- Existing historical specs may describe older route names. Use this guide's
  paths above and the live handlers/protobuf file as the implementation source
  of truth.
